  - **写 java 代码时有一个疑惑**  
    以下两个实现的功能基本相同的方法，哪一种更合理？

    ```java
       public Boolean launch(int index) {
            log.debug("启动指定模拟器 index:"+ index);
            CMD.executeSingleCommand(Config.ldconsole_path + " launch --index " + index, 20, TimeUnit.SECONDS);// 执行启动命令
            SysUtil.sleep(1000);
            String status = listALl().get(index).split(",")[4];
            return status.equals("2")||status.equals("1");
        }
        public void launch(int index) {
            log.debug("启动指定模拟器 index:"+ index);
            CMD.executeSingleCommand(Config.ldconsole_path + " launch --index " + index, 20, TimeUnit.SECONDS);// 执行启动命令
            SysUtil.sleep(1000);
            String status = listALl().get(index).split(",")[4];
            if (!status.equals("2")&&!status.equals("1")){
                throw new RuntimeException("模拟器未失败");
            }
        }
    ```

  - **分析**

    1. **方法的设计**

       - ​**​`Boolean launch(int index)`​** ：

         - 该方法返回一个 `Boolean` ​值，表示模拟器是否成功启动。通过返回值，调用者可以进一步处理启动是否成功的逻辑。
         - 该方法返回一个 Boolean 值，表示模拟器是否成功启动。通过返回值，调用者可以进一步处理启动是否成功的逻辑。
       - ​**​`void launch(int index)`​** ：

         - 该方法没有返回值。如果模拟器启动失败，会直接抛出一个 `RuntimeException` ​异常。
         - 适用场景：调用者不关心启动是否成功，而是想要通过异常机制来通知问题发生，并立即终止执行。适合在确保模拟器启动失败时，整个流程不继续执行的场景。
    2. **错误处理**

       - ​**​`Boolean launch(int index)`​** ：

         - 使用 `return`​ ​返回 `true`​ ​或 `false` ​来表示启动成功与否。这种方式非常直观，但调用者需要手动判断返回值，并根据结果进行处理。
         - 错误处理的灵活性较低。调用者虽然能得到结果，但如果出现启动失败的情况，可能无法获取更多的上下文信息。
       - ​**​`void launch(int index)`​** ：

         - 该方法通过抛出 `RuntimeException` ​来进行错误处理。异常机制的好处是，当出现启动失败时，可以立即终止程序的当前执行并捕获异常（如果在调用时有适当的异常处理机制）。这对于某些场景（如需要保证模拟器成功启动才能继续后续操作的情况）更加有效。
         - 这种方式适合流程控制较为严格的系统，能够避免继续执行无效的操作。
    3. **可读性和易于理解性**

       - ​**​`Boolean launch(int index)`​** ：

         - 返回布尔值的方式非常直观，调用者清楚知道返回的是一个成功或失败的标志。
         - 对于大部分场景，这种设计较为常见和易于理解。
       - ​**​`void launch(int index)`​** ：

         - 使用异常来表示错误的处理方式略显激进，特别是在没有明确处理异常的情况下，可能会使代码的可读性降低。调用者需要明确知道如果失败会抛出异常，且需要捕获这个异常。
    4. **健壮性与可扩展性**

       - ​**​`Boolean launch(int index)`​** ：

         - 这种设计可以为后续扩展提供灵活性，例如，调用者可以根据 `true`​/`false` ​的返回值做进一步的决策（如重试、日志记录等）。
         - 如果模拟器启动过程复杂，后续扩展可能更容易通过返回值来进行灵活处理。
       - ​**​`void launch(int index)`​** ：

         - 异常的方式能有效简化代码中对失败的控制，尤其是在需要严格控制流程的场景下，异常能够避免无用的后续操作。
         - 但异常机制可能不利于一些场景下的灵活扩展，特别是在调用者希望根据不同状态执行不同操作的情况下。
    5. **性能**  
       从性能角度，两种方法没有本质的差异，因为都涉及到相同的命令执行和状态检查操作。唯一的差别在于错误处理方式：返回值方式相对轻量，而异常方式可能在捕获异常时会有一定的性能开销，尤其是在异常不频繁发生的场景下。
  - **总结**

    - ​**​`oolean launch(int index)`​**  适用于：

      - 希望通过返回值直接获得启动结果的场景，调用者可以根据返回值做进一步处理。
      - 错误处理相对简单，但调用者需要自行判断和处理结果。
    - ​**​`void launch(int index)`​**  适用于：

      - 希望通过异常机制中断不成功的启动操作，确保出现问题时不继续执行后续操作。
      - 适合那些无法容忍启动失败且希望立即反馈错误的场景。
  - **个人总结**

    - ​**​`Boolean launch(int index)`​** ​ 适合**需要明确知道方法的执行结果，且方法执行失败对于程序来说不是致命错误的场景，**
    - ​**​`void launch(int index)`​** ​ 适合**流程管理，执行到某一步流程时出错，停止流程，并抛出异常告知程序出现错误的位置**

  - ## 注释和注解是写在接口还是实现类上？
  - ### 注解

    ```mermaid
    graph TD
        A[需要添加注解] --> B{注解的作用目标?}
        B --> |技术实现类<br>（如 @Transactional, @Cacheable）| C[放在实现类]
        B --> |行为契约类<br>（如 @Override, @FunctionalInterface）| D[放在接口]
        B --> |API文档类<br>（如 @Api, @Schema）| E[接口写通用描述, 实现类写细节]
        C --> F[检查代理机制是否兼容]
        D --> G[确保接口纯净性]
        E --> H[避免内容重复]
    ```

    **规则说明**：

    - **技术实现类注解**：必须放在实现类（避免污染接口）。
    - **契约类注解**：放在接口（定义行为规范）。
    - **文档类注解**：接口描述整体功能，实现类补充细节。
  - ### 注释

    ```mermaid
    graph TD
        A[需要添加注释] --> B{注释内容类型?}
        B --> |方法契约/规范<br>（如功能、参数、返回值）| C[必须写在接口]
        B --> |实现细节<br>（如算法、性能优化）| D[写在实现类]
        B --> |通用逻辑说明| E[接口写概要, 实现类补充细节]
        C --> F[确保所有实现类遵守契约]
        D --> G[避免重复接口注释]
        E --> H[保持同步更新]
    ```

    **规则说明**：

    - **接口注释**：定义核心契约（方法作用、参数、返回值、异常）。
    - **实现类注释**：只写差异化内容（如优化逻辑、特殊处理）。
    - **同步性**：接口注释修改时，需检查实现类注释是否冲突。
  - ### **对比总结表**

    |**维度**|**注解（Annotation）**|**注释（Comment/Javadoc）**|
    | --| -------------------------------------------| ------------------------------|
    |**核心目标**|控制技术行为或生成元数据|解释代码逻辑，提高可读性|
    |**接口位置**|仅限契约类注解（如 @FunctionalInterface）|必须写方法契约和规范|
    |**实现类位置**|技术实现类注解（如 @Transactional）|只写实现细节，避免重复|
    |**关键原则**|接口与技术解耦|接口定义行为，实现类描述细节|
    |**反例**|@Transactional 写在接口|在实现类重复接口的Javadoc|
  - ### **伪代码示例**

    - **注解示例**

      ```java
      // 接口：定义契约
      @FunctionalInterface
      public interface PaymentService {
          void pay(BigDecimal amount);
      }

      // 实现类：添加技术注解
      @Service
      public class PaymentServiceImpl implements PaymentService {
          @Override
          @Transactional  // ✅ 技术注解放在实现类
          public void pay(BigDecimal amount) {
              // 实现
          }
      }
      ```

    - **注释示例**

      ```java
      // 接口：完整方法契约
      public interface UserService {
          /**
           * 根据ID查询用户（接口必须注释）
           * @param id 用户ID，不能为null
           * @return 用户对象，不存在时返回null
           * @throws IllegalArgumentException 参数无效时抛出
           */
          User getUserById(Long id);
      }

      // 实现类：补充实现细节
      public class UserServiceImpl implements UserService {
          @Override
          public User getUserById(Long id) {
              // 使用二级缓存优化查询（实现类注释写细节）
              return cache.get(id, () -> dao.queryById(id));
          }
      }
      ```

    - 这个错误信息表明在连接MySQL数据库时遇到了一个问题，具体是与“Public Key Retrieval is not allowed”相关的错误。该错误通常发生在MySQL数据库配置中启用了基于SHA-256密码插件的身份验证，并且未允许通过非安全连接检索公钥。解决这个问题的方法有以下几种：

      ### 解决方案

      #### 1. **修改数据库连接字符串**

      在连接MySQL时，你需要在连接字符串中加入`allowPublicKeyRetrieval=true`参数。这将允许客户端检索公钥并进行身份验证。

      修改前：

      ```plaintext
      jdbc:mysql://your-database-url:3306/your-database-name
      ```
      修改后：

      ```plaintext
      jdbc:mysql://your-database-url:3306/your-database-name?allowPublicKeyRetrieval=true&useSSL=false
      ```
      ### 参数说明：

      - ​`allowPublicKeyRetrieval=true`：允许公钥检索。
      - ​`useSSL=false`：禁用SSL（如果你的环境不要求SSL，可以禁用，否则根据需求启用）。

      #### 2. **调整MySQL数据库配置**

      如果你的数据库环境使用的是较新的MySQL版本（8.0及以上），并启用了基于SHA-256密码插件的身份验证，可能需要更改MySQL服务器的配置以允许公钥检索。

      编辑MySQL配置文件（通常是`my.cnf`​或`my.ini`），添加或修改以下内容：

      ```ini
      [mysqld]
      # 允许客户端进行公钥检索
      caching_sha2_password_auto_generate_rsa_keys=1
      ```
      保存并重新启动MySQL服务。

      #### 3. **更新MySQL用户的身份验证插件**

      另一种解决方法是将MySQL用户的身份验证插件更改为`mysql_native_password`​，而不是`caching_sha2_password`。这可以通过以下SQL语句进行操作：

      ```sql
      ALTER USER 'your-username'@'your-host' IDENTIFIED WITH mysql_native_password BY 'your-password';
      ```
      这将使数据库用户使用传统的`mysql_native_password`​身份验证方式，从而避免使用`caching_sha2_password`插件。

      ### 4. **检查防火墙和网络连接**

      确保MySQL服务器的端口（通常是3306）没有被防火墙阻塞，并且数据库服务器本身是可以访问的。有时候即使是数据库配置正确，网络问题也会导致连接失败。

      ### 总结

      - 确保连接字符串正确设置了`allowPublicKeyRetrieval=true`。
      - 如果需要，可以在MySQL数据库端进行配置修改，或者更改用户的身份验证插件为`mysql_native_password`。
      - 还需要检查防火墙和网络连接是否正常。
